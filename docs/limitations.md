# Обмеження BenchLevel без ОС

Актуальні S1/S2/S3 та відкриті перевірки наведено у [результатах](lab3-results-20261101.md). Host-модель не вимірює затримку flash, джитер MCU або втрату живлення.

## 1. Резерв постійних даних забирає місце програми

Симптом: первинна реалізація потребувала 30 576 байтів при 28 672 байтах code region. Linker відмовився, overflow 1904 B. Виміряна збірка займає 27 652 B, запас code region 1020 B; ще 4096 B належать сховищу.

Причина: програма і два покоління калібрування ділять 32 КБ однобанкової flash. Обхід без ОС: LTO, спільний atan2f замість другого трансцендентного алгоритму та обмежений integer formatter. Вартість: складніша атрибуція розміру, власні тести формату. RTOS додасть код і дані, тому сама не усуває цю межу. Гіпотеза ЛР4: після додавання лише необхідних механізмів ОС приріст code flash має залишитися ≤1020 B; якщо ні, ця конфігурація не поміститься. Це критерій майбутньої перевірки, не обіцянка.

## 2. Одна flash-операція монополізує foreground

Доказ коду: `Platform/calibration_flash.c` викликає справжні HAL_FLASHEx_Erase і HAL_FLASH_Program; цикл не виконує інші foreground задачі, доки виклик не повернеться. На фізичному C031 доступи до тієї ж flash можуть затримувати виконання та ISR. Одна doubleword за крок зменшує блок, але не розбиває page erase. Джитер від цього ще не виміряний на MCU.

Обхід без ОС: виконувати з RAM усі потрібні шляхи разом із векторами й даними, або відкласти SAVE до безпечного вікна; це окремий бюджет RAM і складніший linker contract. RTOS дасть storage task і пріоритети для роботи між операціями, але не скасує stall однобанкової flash. Вартість ОС: стек worker, черга запитів, взаємне виключення. Гіпотеза ЛР4: command latency між doubleword не перевищить 20 мс за штатного потоку; пауза всередині page erase залишиться, якщо шляхи не перенесені в RAM. Потрібні PA6/RX/PB1 записи, зараз максимум не підтверджено.

## 3. Передача відповіді затримує розбір наступної команди

Доказ коду: `command_step` повертається, поки TX зайнятий, а STATS послідовно виводить одинадцять рядків. Буфер RX має 256 позицій, одна залишається порожньою, місткість 255. Це не безмежна черга. UART фізично має 11 520 байтів/с при 115200 8N1. Навіть без flash сума STATUS+EVT обмежує командний потік.

Обхід без ОС: окрема черга відповідей, незалежний розбір команд і rate limiting. Вартість: додаткові буфери, правила відмови й узгодження snapshot. RTOS: RX task високого пріоритету, TX worker і bounded queue дозволять виконати дію до завершення попереднього виводу. Вартість: окремі стеки, синхронізація, ризик інверсії пріоритетів. Гіпотеза ЛР4: за 10 команд/с максимум дії ≤20 мс під STATS; нестійкий потік вище фізичної пропускної здатності залишиться нестійким. Реальна точка зламу має бути виміряна `boundary`, зараз вона відкрита.

## 4. Час задач і спільний MSP мають неповну спостережуваність

Доказ: `perf.c` має крок HAL tick 1 мс, а не DWT на кожен такт; `.su` після LTO дає лише збережені кадри, частина викликів вбудована в main. Paint не чіпає активний стек. Спостережений watermark становить 668 B, але не є доказом повної глибини. Резерв 4096 B і heap minimum 512 B підтверджені linker script.

Обхід без ОС: контрольні GPIO, вимір накладних витрат, довгий прогін усіх гілок, аналіз бібліотек і вкладення ISR. RTOS дасть окремі high-watermark по задачах, але idle/IRQ стек і невиконані шляхи також потребують перевірки. Вартість: кожен резерв задачі витрачає RAM, навіть коли задача не працює. Гіпотеза ЛР4: після тривалого S2 сумарний зарезервований RAM залишиться ≤12 КБ, кожен стек матиме щонайменше 25% спостереженого запасу. Порівняння повинно включати всі стеки, а не тільки найбільший.

## 5. Кооперативний запит не гарантує фізичний період відліку

Доказ коду: `controller_step` веде фазову сітку `sample_period`, але `mpu_request` приймається тільки у MPU_READY. Пропущені слоти не наздоганяються циклом багатьох читань. Навіть у простому продукті треба окремо рахувати releases, готові придатні samples, late і skipped. Host-тести підтверджують backoff/timeout та wrap, але не реальну частоту шини.

Обхід без ОС: DRDY IRQ і bounded sample queue, апаратний запуск або точніша FSM. У Wokwi DMA для C031 не підтримується, його не можна оголосити перевіреним обходом. RTOS: task notification від DRDY і пріоритет sensor task зменшать затримку foreground, якщо CPU виконує код. Вартість: черга відліків, політика переповнення і старіння даних. Гіпотеза ЛР4: максимум запізнення штатного 50 мс запиту в S3 ≤5 мс поза flash stall, а skipped=0 у S2. Потрібне порівняння максимумів, не середніх.

## 6. Цілісність збереження вимагає окремого протоколу

Фактичний доказ: `test_lab3.c` виконав 38 варіантів відсікання операцій, 512 одиночних пошкоджень бітів і повторну спробу після часткового запису. `calibration_store` використовує 64-байтовий запис, CRC-32, інверсію sequence і останній doubleword commit. Ротація стирає альтернативну сторінку, зберігаючи останній цілий результат. Це доводить протокол на host-моделі, а не електричну стійкість flash.

Обхід без ОС вже реалізований, але він має scan, phase, verify і відновлення destination. OS worker може ізолювати цей стан і серіалізувати запити через queue; RTOS не замінить CRC/commit і не зробить частковий запис атомарним. Вартість: worker stack, буфер повідомлень, зупинка або відхилення SAVE при переповненні. Гіпотеза ЛР4: ті самі 38 відсікань та 512 пошкоджень не змінять результатів, а foreground latency покращиться лише між операціями. Фізичне вимкнення живлення й збереження даних після нього залишаються окремим відкритим випробуванням.

## Що варто зберегти без ОС

У BenchLevel немає окремих стеків задач і динамічних прикладних алокацій. Стан кутів і калібрування змінює один foreground owner. Нормальна I²C транзакція виконується через ISR, а обмежений CAL/ADC не потребує блокувальних затримок. У ЛР4 слід перевірити, чи виграш реакції виправдає додаткові RAM/flash і синхронізацію. Стверджувати потребу ОС за ще не отриманими часовими числами не можна.
